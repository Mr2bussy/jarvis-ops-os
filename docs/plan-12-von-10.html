Zwölf von Zehn

Acht Dimensionen, heute im Schnitt bei 5. Der Weg auf 10 ist Arbeit. Der Weg auf 12 ist etwas anderes: ein Mechanismus, der den Rückfall unmöglich macht.

10 heißt: die Eigenschaft ist da.
12 heißt: sie kann nicht mehr verloren gehen.

Dieses Projekt war schon einmal bei 8 — 431 grüne Tests, lückenloser IPC-Vertrag, ein Vault mit 121 Agenten. Innerhalb von drei Tagen ist alles davon verfallen, weil nichts es festgehalten hat. Jede Dimension unten bekommt deshalb eine Sperrklinke: eine Prüfung, die den Build rot färbt, sobald die Eigenschaft verschwindet. Nicht ein Dokument, das behauptet, sie sei da.

Sperrklinke 🔒 D2

Argumentprüfung statt Musterliste, Property-Fuzz mit 10 000 generierten Pfaden, und ein Bedrohungsmodell, in dem jede Angriffskette einen Test hat, der die Sperre beweist.

Der eigentliche Fix. Heute entscheidet ein Regex über die ganze Befehlszeile (/^(type|cat)\s+[^\s]+\s*$/i), und ein Treffer läuft ohne Gate. Stattdessen:

  • Befehl in Kommando und Argumente zerlegen — nie die ganze Zeile mustern.
  • Kommando gegen die Allowlist, danach jedes pfadartige Argument durch isPathInRoots().
  • Alles Übrige fällt auf requiresAdvancedMode: true zurück.

Sperrklinke 🔒 D4

Die IPC-Verträge werden generiert. Damit verschwindet eine ganze Fehlerklasse — sie wird nicht mehr gefunden, sie kann nicht mehr entstehen.

Heute steht dieselbe Wahrheit an drei Orten: preload.ts, global.d.ts und die Handler in main.ts. Drei Orte, die auseinanderlaufen können — und gestern noch taten (jarvis:gemini-transcribe ohne Aufrufer, elf employee:*-Handler ohne Konsument). Stattdessen eine Quelle:

// electron/ipc/registry.ts — die einzige Wahrheit
export const CHANNELS = {
  'jarvis:complete': { schema: CompletePayload, risk: 'B', handler: handleComplete },
  'mt5:positions':   { schema: Mt5Query,       risk: 'A', handler: handleMt5Positions },
} as const;
pnpm gen:ipc           # erzeugt preload.ts, global.d.ts, docs/IPC.md
pnpm gen:ipc --check   # in CI: rot, wenn generiert ≠ eingecheckt

„Kanal ohne Handler", „Handler ohne Schema", „Typ ohne Implementierung" sind danach keine Testfälle mehr, sondern Konstruktionsfehler, die der Generator gar nicht erzeugen kann.

Sperrklinke 🔒 D5

Herkunft wandert ins Typsystem: Eine Zahl ohne Quelle lässt sich nicht mehr rendern — sie ist ein Compilerfehler, keine Frage der Disziplin.

// src/lib/sourced.ts
export type Sourced<T> = {
  value: T;
  source: 'measured' | 'catalog' | 'none';
  at?: number;     // wann gemessen
  from?: string;   // woher, z. B. 'vault-scan' oder 'mt5:1234'
};
  • Panels rendern ausschließlich über <Value data={sourced} />, das die Herkunftsmarke selbst zeichnet.
  • ESLint verbietet nackte Zahlenliterale in JSX unterhalb von src/screens/**.
  • offlineJarvisReply() liefert { text, degraded: true, reason } — die Oberfläche zeigt ein Warnband statt einer Antwort, die klingt, als sei JARVIS dumm geworden.
  • Der Selbsttest läuft beim Start und erscheint als Health-Karte auf der Bridge, nicht versteckt in Admin.

Das ist die Dimension mit dem größten Hebel. Wenn eine sichtbare Zahl nachweislich erfunden ist — „187 agents" bei null vorhandenen Dateien — glaubt der Operator auch den echten nicht mehr. Dann ist die gesamte Oberfläche wertlos, egal wie gut der Rest funktioniert.

Sperrklinke 🔒 D7

Ein Tag genügt: bauen, signieren, veröffentlichen — und ein Runner nimmt den Installer automatisch ab, bevor irgendjemand ihn bekommt.

  • release.yml auf tags: v* — electron-builder --win --publish always mit CSC_LINK und CSC_KEY_PASSWORD.
  • Installer-Rauchtest auf frischem Windows-Runner: still installieren, starten, production:dry-run abfragen, Health prüfen, deinstallieren.
  • SBOM ans Release, Vorgängerversion bleibt als Rollback im Update-Feed.

Die Falle, die eine gepackte App leer starten lässt: app.isPackaged schaltet das Lesen der .env ab (electron/config/store.ts:55). Alles, was heute nur dort steht — ANTHROPIC_API_KEY, GITHUB_TOKEN, JARVIS_MODEL, JARVIS_AGENTS_PATH — muss vorher in den safeStorage. In der Entwicklung fällt das nie auf.

  • Sprachlatenz-Ziel p95 unter 3 s. Gemessen im Log: 25–30 s pro Antwort ([VOICE] hermes-agent ok · 27164ms). Reißt das Ziel, färbt das Error-Budget den Sprachmodus sichtbar rot, statt dass der Operator wartet und rät.

  • Tokens als einzige Farbquelle — kein Hex-Literal im Komponentencode, per ESLint erzwungen.

DER BEWEISEin Befehl, nicht ein Bericht

Der Grund, warum dieses Projekt gestern „50 DONE / 0 PARTIAL" meldete, während die Suite rot war: Der Fortschritt wurde erzählt statt gemessen. Ab hier gibt es genau eine Instanz, die das beantwortet.

pnpm verify
"verify": "node scripts/doctor.mjs --tree
  && node scripts/scan-secrets.mjs --fail-on-new
  && pnpm exec eslint . --max-warnings=9999
  && pnpm exec tsc -p tsconfig.json --noEmit
  && pnpm exec tsc -p electron/tsconfig.json --noEmit
  && pnpm gen:ipc --check
  && pnpm test:cov
  && node scripts/coverage-ratchet.mjs
  && pnpm exec depcruise --config .dependency-cruiser.cjs electron src
  && pnpm exec playwright test"

Zwölf von zehn ist erreicht, wenn dieser Befehl grün ist, bei jedem Push in der CI läuft und main ohne ihn nicht beschreibbar ist. Ein Statusdokument kann das nicht ersetzen — es hat es hier bereits versucht.
